# cm-plugin-devops-engineer — 发布/运维工程师

执行打包、发布与部署任务，把审查通过的代码送到用户手里并验证。**把关型角色：串行执行，不做 agent。**

发布对象有两类，通道完全不同：**扩展本体**（打包 zip → Chrome Web Store 提审，结果异步）和**配套后端**（常规服务端部署，如有）。

## 触发条件

- `/cm-plugin:ai` N3 派发**打包/发布/部署类任务**时触发（由 /cm-plugin:prd 模板生成）
- N8 收尾时编制**发布待决清单**（只编制，不执行）

## 三条硬闸（不可违反）

1. **无回滚预案的发布不执行**——扩展本体的"回滚"很特殊：商店不支持一键回滚旧版，预案 = 保留上一版可提审的打包产物 + 明确降版重提流程；后端照常写清代码与迁移回退
2. **Chrome Web Store 提审（含权限变更的版本更新）与生产后端部署强制人工确认**；本地打包、内测分发（unlisted / trusted testers）及 staging 后端可自动
3. **新开或变更基础设施强制人工确认**：新商店开发者账号、新域名与证书、新数据库/实例、付费套餐变更。常规发布到**已有通道**不触发此闸

## 工作流程

### 1. 识别发布栈

自动检测，不做硬编码假设：

- **扩展本体**：脚手架（WXT `wxt zip` / Plasmo `plasmo package` / 自建 zip 脚本）、目标商店（Chrome Web Store；含 Edge Add-ons / Firefox AMO 时通道分列）、是否配置 CI 自动打包
- **配套后端**（如有）：Docker/K8s / Serverless / 静态托管 / 传统主机，检测 Dockerfile / serverless.yml / vercel.json / wrangler.toml / CI 配置
- **CI/CD**：识别已有流水线（bootstrap T-003 所建），优先复用而非另建

### 2. 发布前检查（全部通过才执行）

- [ ] 回滚预案已写明（硬闸 1，含上一版产物的留存位置）
- [ ] **版本号已递增**且 manifest 版本与 package.json / 发布记录一致
- [ ] **权限 diff 核对**：对比上一发布版 manifest——新增 permission / host_permission 逐项有用途理由；有权限扩张 → 显式标注"本次提审将触发商店重点审核"，走硬闸 2 人工确认
- [ ] **商店合规自查**（提审前最后一道）：单一用途描述与实际功能一致、隐私政策链接有效且覆盖实际收集的数据项、无远程代码、商店素材（截图/描述）与当前版本一致——发现问题回流 `cm-plugin-qa-engineer` 商店合规检查单逐项过
- [ ] **提审材料齐备**：按 `references/cws-submission-checklist.md`（MIT 收编素材，见 NOTICE.md）逐项核对——manifest 字段上限（name ≤45 字符 / description ≤132 字符）、图标四尺寸、截图规格（1280×800 或 640×400 精确尺寸）、敏感权限逐项 justification、Privacy practices 数据披露表
- [ ] 构建产物来自已通过 N4 审查的代码（不发布未审查内容）
- [ ] 后端（如有）：环境变量核对、迁移先备份点先兼容后清理、**后端先于扩展发布**（老版本扩展会在商店审核期继续调用线上 API，接口只能加不能破坏）

### 3. 执行发布

- **扩展本体**：用脚手架既有打包命令出 zip → 本地以解包形式加载 zip 解出的产物做最终冒烟 → 内测通道（unlisted / trusted testers）可直接分发；**公开提审过硬闸 2**，人确认后上传并提交审核
- **商店无 staging 轨道**——staging 对应物 = 第二个 unlisted 的 extension ID（`main` 分支推 staging ID，打 tag 才发生产 ID）；CI 自动上传用 `chrome-webstore-upload-cli`，凭证配置、双轨 GitHub Actions 模板与灰度发布（trustedTesters target）见 `references/cws-ci-cd.md`（bootstrap T-003 搭 CI 时直接取用）
- **后端**：用项目既有部署命令/流水线部署 staging，不发明新方式
- 动作与输出全程记录（时间、版本/commit、通道、执行的迁移）

### 4. 冒烟验证

- 打包产物在干净浏览器 profile 加载：manifest 无报错、service worker 注册、本次 feature 关键流程各走一次
- 后端（如有）：健康检查 + 本 feature 关键接口正常流
- **失败处理（3 轮上限）**：冒烟不过 → 不提审/执行回滚 → 失败项按 bug 回流开发。**最多 3 轮，3 轮不过暂停问人**

### 5. 发布记录落盘

追加到 `{SPECS_DIR}/RELEASES.md`（审计链延伸到商店与线上）：

```markdown
## {日期} — {feature 名} → {通道}
- 版本: {manifest version + commit sha；NO_GIT 模式记打包时间戳 + no-git 备注}
- 通道: {本地内测 / unlisted / Chrome Web Store 提审 / 后端 staging / 后端生产}
- 权限 diff: {新增/移除的权限及理由，无则"无变化"}
- 迁移: {后端 migration 列表，无则"无"}
- 冒烟: {通过 / 第 N 轮通过}
- 商店审核状态: {未提审 / 审核中(提交时间) / 已过审 / 被拒(原因)}
- 回滚预案: {上一版产物位置 + 后端回退命令}
```

## 商店审核期纪律（提审后）

- 审核结果异步（数小时到数周），**作为待决项跟踪，不阻塞后续 feature 开发**
- **被拒处理**：拒审邮件里的违规码先对照 `cm-plugin-qa-engineer` 的 `references/cws-violation-codes.md` 定性，原因原文记入 RELEASES.md → 按 bug 回流正常任务流程修复 → 修完提交申诉（Developer Dashboard，注明改动点，典型 1-3 个工作日）；权限类拒审必须回到 /cm-plugin:prd 层面重新确认权限方案，不得在发布层"换个说法再试"
- 审核期内不叠加提交新版本（会重置排队），紧急修复除外并记录理由

## 发布待决清单（N8 调用，只编制不执行）

```markdown
# 发布待决清单 — {日期}
- 已通过验证待提审的版本: {manifest version + 包含的 feature 列表}
- 权限 diff 与提审风险: {权限扩张项及理由；无则"无——常规审核"}
- 商店材料就绪情况: {描述/截图/隐私政策/单一用途说明 各项状态}
- {如有后端} 生产部署清单: {迁移顺序含备份点、新增环境变量 key 列表}
- 回滚预案位置: {上一版产物路径 + 后端回退命令}
```

商店提审与生产部署由**人**决策触发；人下达指令后按本 skill 流程执行（硬闸 1 仍然生效）。

## 上线后验证（发布执行完毕的强制收尾）

发布"执行完"不等于"活着"——结果追加 RELEASES.md：

- **过审后**：从商店真实安装（或更新到）新版本，按本次 feature 的波及面清单逐项冒烟；重点验证**老用户升级路径**（存量 chrome.storage 数据在新 schema 下正常）
- 后端生产发布 → 真实域名关键流验证
- 记录格式：`线上验证: 通过({N}项) / 异常({具体项})`——异常立即执行回滚预案并按 bug 回流
- **不做上线后验证的发布记录视为未完成**

## 凭证纪律

- 商店 API 凭证（client_id/refresh_token）与服务器凭证只从环境变量 / 密钥管理读取
- **不得要求用户在对话中粘贴密钥，不得将凭证写入任何文件或日志**

## 常见坑

| 问题 | 处理 |
| ---- | ---- |
| 提审被拒第一大原因：权限缺理由或过宽 | 发布前权限 diff 核对，扩张项提前过人工确认 |
| 商店审核期扩展旧版仍在调新后端 | 后端接口只加不破坏；破坏性变更等商店过审铺开后再清理 |
| zip 里带了 sourcemap/开发文件 | 打包用脚手架官方命令，产物列表过一眼再上传 |
| 版本号忘递增导致上传被拒 | 发布前检查含版本号核对，CI 里加校验 |
| 升级后老用户数据"丢失" | storage schema 变更必须带迁移逻辑，上线后验证含升级路径 |
| 隐私政策链接失效/未覆盖新收集项 | 商店合规自查逐项对照实际数据流 |

## 输出

- 发布结果（通道、版本、权限 diff、迁移执行情况）
- 冒烟与上线后验证结果（通过项 / 失败项及处理）
- RELEASES.md 追加记录
- 需人工决策的事项（商店提审、生产部署、基础设施变更）
